Anomaly Upload Validator — User Stories & Acceptance Criteria

Platform A · Internal Tool · v3.1.4 · September 2026

Overview

This document contains the user stories and acceptance criteria for the Anomaly Upload Validator. Stories are organized by epic and reflect delivered functionality as of v3.1.4. Each story follows the format: "As a [persona], I want [capability], so that [outcome]." Acceptance criteria are written as testable, unambiguous conditions.

EP-01 — File Ingestion

Uploading raw source platform exports into the tool.

US-01 — Upload a dataset file

EP-01 — File Ingestion
FieldDetail
PersonaData Coordinator
PriorityMust Have
StatusDone
Versionv1.0

User Story:

As a Data Coordinator, I want to upload a CSV or XLSX file by dragging it into the tool or browsing for it, so that I can begin validating a dataset without needing any technical setup.

Acceptance Criteria

  • AC-01: Tool accepts .csv, .xlsx, and .xls file formats.
  • AC-02: User can drag and drop a file onto the designated drop zone.
  • AC-03: User can alternatively click the drop zone to open a file browser.
  • AC-04: On successful load, the filename and total data row count are displayed.
  • AC-05: If the file is empty or cannot be parsed, a clear error message is shown and no validation runs.
  • AC-06: No file data is transmitted to any external server at any point.

US-02 — Have column names normalized automatically

EP-01 — File Ingestion
FieldDetail
PersonaData Coordinator
PriorityMust Have
StatusDone
Versionv1.0

User Story:

As a Data Coordinator, I want the tool to automatically handle common column name variations in source platform exports, so that I don't have to manually rename columns before uploading.

Acceptance Criteria

  • AC-01: "Date" is treated as "Inspection Date".
  • AC-02: "Blade Chamber" is treated as "BladeChamber".
  • AC-03: "Chord (%)" is treated as "Chord(%)".
  • AC-04: "Turbine Serial Number" is treated as "Serial Number".
  • AC-05: "Links" is treated as "Source Images".
  • AC-06: Unrecognized column names are passed through unchanged and do not cause errors.
  • AC-07: Normalisation is applied silently — no notification shown to the user.

Note: Alias map is defined as a named constant in the tool script. Engineering can extend it without touching validation logic.

US-25 — Upload a file that has a metadata preamble above the header row

EP-01 — File Ingestion
FieldDetail
PersonaData Coordinator
PriorityMust Have
StatusDone
Versionv2.3

User Story:

As a Data Coordinator, I want a file whose header row sits below several rows of metadata to be read correctly, so that I do not have to delete rows by hand before uploading.

Acceptance Criteria

  • AC-01: The header row is located automatically within the first 25 rows of the sheet.
  • AC-02: The row scoring the most recognised column names is chosen as the header.
  • AC-03: Rows above the detected header are ignored and do not become data rows.
  • AC-04: The detected header row number is reported back on the upload confirmation.
  • AC-05: A file whose header is on row 1 is unaffected.

Note: Before v2.3 the tool assumed row 1 was the header, so any export carrying a preamble failed at ingestion.

EP-02 — Validation

Checking datasets against the Platform A upload specification.

US-03 — See which required columns are missing

EP-02 — Validation
FieldDetail
PersonaData Coordinator
PriorityMust Have
StatusDone
Versionv1.0

User Story:

As a Data Coordinator, I want the tool to tell me which required columns are missing from my dataset, so that I can fix the file before attempting an upload.

Acceptance Criteria

  • AC-01: Tool checks for all 18 required column headers after alias normalisation.
  • AC-02: Missing required columns are displayed as individual cards showing field name and description.
  • AC-03: Missing conditional columns (Serial Number, BladeChamber, Chord(%), Recommendation) are shown as informational — they do not block the export.
  • AC-04: Column name matching is case-sensitive.
  • AC-05: Missing column cards appear before the row-level issues table.

US-04 — See which rows have field errors

EP-02 — Validation
FieldDetail
PersonaData Coordinator
PriorityMust Have
StatusDone
Versionv1.0

User Story:

As a Data Coordinator, I want to see exactly which rows have missing or incorrectly formatted required fields, so that I know what needs to be fixed before the dataset can be uploaded.

Acceptance Criteria

  • AC-01: Every data row is validated against all required field rules after normalisation and conversion.
  • AC-02: Each issue is shown with: Row number, Anomaly ID, Field name, Status badge, and detail message.
  • AC-03: Severity must be an integer between 1 and 5 inclusive.
  • AC-04: Critical must be "Yes" or "No" (case-insensitive).
  • AC-05: Inspection Date must match YYYY-MM-DD format exactly.
  • AC-06: "Damage Location" must be "Internal" or "External" (case-insensitive).
  • AC-07: Distance (m), Length (m), Width (m) must be numeric values.
  • AC-08: Coordinates must contain at least three [x,y] bracketed pairs.
  • AC-09: Empty required fields raise an Error, except for Asset and Coordinates (see US-06).

As a Data Coordinator, I want the tool to accept both abbreviated codes and full descriptive names for Blade Side values, so that datasets using either naming convention pass validation without manual editing.

User Story:

As a Engineering / Data Lead, I want conditional field format issues to appear as Warnings rather than Errors, so that they don't inflate the error count or block the export.

Acceptance Criteria

EP-04 — Conversion Engine

Transforming Input Source field values across three nomenclature systems.

US-10 — Have Element values derived and converted automatically

EP-04 — Conversion Engine
FieldDetail
PersonaData Coordinator
PriorityMust Have
StatusDone
Versionv2.0 / v2.1

User Story:

As a Data Coordinator, I want the tool to automatically build the Input Source Component value from the raw data columns and look up its Platform A and Platform B equivalents, so that I don't have to manually apply conversion formulas.

Acceptance Criteria

  • AC-01: If Material column is present and non-empty: Input Source Component = Component + " - " + Material.
  • AC-02: If Material is absent/empty but Element column is present: Input Source Component = Component + " - " + Element.
  • AC-03: If neither suffix column is present/populated: Input Source Component = Component alone.
  • AC-04: Concatenation uses a LEN()=0 guard — not ISBLANK() — to correctly handle empty-string cells.
  • AC-05: If found in conversion table, Platform A Element and Platform B Element are populated from columns B and C.
  • AC-06: If not found, both columns show "MANUAL REVIEW: [original value]" and the row is flagged.

Note: Multi-format support (Material vs Element fallback) and ISBLANK→LEN fix added in v2.1.

US-11 — Have Anomaly Type values derived and converted automatically

EP-04 — Conversion Engine
FieldDetail
PersonaData Coordinator
PriorityMust Have
StatusDone
Versionv2.0 / v2.1

User Story:

As a Data Coordinator, I want the tool to automatically build the Input Source Damage Type value and look up its Platform A and Platform B equivalents, so that damage type conversion happens without any manual steps.

Acceptance Criteria

  • AC-01: If Type column is present, it is used as the base value.
  • AC-02: If Type is absent but Anomaly Type column is present, it is used as the base value.
  • AC-03: If Subtype is present and non-empty: Input Source Damage Type = base + " - " + Subtype.
  • AC-04: If Subtype is absent or empty: Input Source Damage Type = base value alone (no trailing " - ").
  • AC-05: Concatenation uses a LEN()=0 guard — not ISBLANK().
  • AC-06: If found in conversion table, Platform A Anomaly Type and Platform B Anomaly Type are populated.
  • AC-07: If not found, both columns show "MANUAL REVIEW: [original value]".

Note: Type vs Anomaly Type column fallback added in v2.1. Fixes the trailing dash bug.

US-26 — Open image links directly from the exported report

EP-07 — Export
FieldDetail
PersonaData Coordinator
PriorityShould Have
StatusDone
Versionv2.6–v2.7

User Story:

As a Data Coordinator, I want the image links in the exported report to be clickable, so that I can open a referenced image without copying a URL out of a cell.

Acceptance Criteria

  • AC-01: Cells in the Links and Source Images columns holding an http or https value carry a real hyperlink.
  • AC-02: The URL remains visible as the cell's display text.
  • AC-03: Source Image Reference is left as plain text, being an identifier rather than a URL.
  • AC-04: The exported URL is byte-for-byte identical to the URL in the source file.
  • AC-05: Where the source cell shows a friendly label but carries a hyperlink, the underlying URL is used rather than the label.

Note: AC-04 is the v2.7 fix. Reading a hyperlink returns its XML entities still encoded, and writing it back encodes them a second time; the resulting URL failed signature matching at the storage provider. Entities are now decoded on ingestion. Links are time-limited by the source system, roughly a 30 day window, which the tool does not yet warn about.

US-27 — Distinguish the blade from the two serial numbers in the output

EP-07 — Export
FieldDetail
PersonaEngineering / Data Lead
PriorityMust Have
StatusDone
Versionv2.5

User Story:

As an Engineering / Data Lead, I want the blade identifier and the two serial numbers to occupy separate output columns, so that the Asset field means one thing and the upload is not carrying a turbine number where a blade letter belongs.

Acceptance Criteria

  • AC-01: Asset (D) carries the blade letter, A to C, and nothing else.
  • AC-02: Turbine Serial Number (E) carries the value the input supplies in its Asset column.
  • AC-03: Asset Serial Number (F) carries the value the input supplies as a serial number.
  • AC-04: The blade letter resolves from a dedicated Blade column, a Blade Position column, a full label such as "Blade A: (No Serial Number)", or a bare letter.
  • AC-05: Blade no longer exists as a separate output column; Asset represents it.

Note: Before v2.5 the output Asset column carried turbine numbers rather than blade letters. The v2.5 insertion shifted every column after D by one position, which is the root of the width misalignment later fixed at v3.1.1.

EP-08 — Output Fidelity

Four stories covering defects where the tool produced output that looked correct and was not. Each was found after v2.1 and fixed between v2.7.1 and v3.1.4.

US-21 — Read output headers that spell both company names correctly

EP-08 — Output Fidelity
FieldDetail
PersonaEngineering / Data Lead
PriorityMust Have
StatusDone
Versionv2.7.1

User Story:

As an Engineering / Data Lead, I want the derived output column headers to render both company names as those companies write them, so that a downstream consumer matching on header text does not have to match two spellings of the same name.

Acceptance Criteria

  • AC-01: All four previously misrendered headers (columns P, Q, U, Y) render their company name correctly.
  • AC-02: The four headers that were already correct (R, V, W, Z) are unchanged.
  • AC-03: Output column count and order are identical to the previous release.
  • AC-04: The export formulas still resolve to the correct column letters, since the corrected strings are also the keys the formula builder reads.
  • AC-05: Files exported before this release still ingest unchanged; no input alias was added or removed.
  • AC-06: Verification reads the header row from the raw exported file, not from a summary or a description of it.

Note: The misrendered strings were a single namespace inside the tool — output header, row key, conversion-field label, Manual Review dropdown key and formula lookup key at once. Correcting only the header text would have broken the formulas. LIM-07 is closed by this story.

US-22 — Have dates arrive intact regardless of my timezone

EP-08 — Output Fidelity
FieldDetail
PersonaData Coordinator
PriorityMust Have
StatusDone
Versionv3.0

User Story:

As a Data Coordinator, I want an inspection date to reach the export as the date the file actually contains, so that I am neither shipping the wrong day nor clearing a validation error on every dated row.

Acceptance Criteria

  • AC-01: A date read from a CSV produces the same calendar date in every timezone.
  • AC-02: A date read from an XLSX date cell produces the same calendar date in every timezone.
  • AC-03: An ingested date is normalised to YYYY-MM-DD, so it satisfies the date rule the validator applies to it.
  • AC-04: No row raises a date-format error solely because of how the date was parsed.
  • AC-05: A cell carrying a real time of day retains it rather than being truncated to a bare date.
  • AC-06: Verified across seven timezones spanning UTC-10 to UTC+14, against both CSV and XLSX inputs.

Note: Two faults with one cause: the ingestion path preferred the parser's display formatting over the underlying value. The timezone shift affected CSV inputs only; the format fault affected both input kinds everywhere, including UTC.

US-23 — Have every column I supply reach the export

EP-08 — Output Fidelity
FieldDetail
PersonaData Coordinator
PriorityMust Have
StatusDone
Versionv3.1

User Story:

As a Data Coordinator, I want a column I supplied to carry its values into the export, so that a blank column means the data was absent rather than lost.

Acceptance Criteria

  • AC-01: Blade Chamber carries its values into the export when the input supplies them.
  • AC-02: Chord (%) carries its values into the export when the input supplies them.
  • AC-03: Chord (%) is written as a number, consistent with the other numeric measurement columns.

US-24 — Read the exported report without resizing columns

EP-08 — Output Fidelity
FieldDetail
PersonaData Coordinator
PriorityShould Have
StatusDone
Versionv3.1.1–v3.1.4

User Story:

As a Data Coordinator, I want each column in the exported report to be wide enough for what it holds, so that I can read a delivered file without resizing columns by hand.

Acceptance Criteria

  • AC-01: The width list holds exactly one entry per output column.
  • AC-02: Each width applies to the column it was written for, not to its neighbour.
  • AC-03: Every conversion-driven column seats its widest possible value without clipping.
  • AC-04: Columns whose content the tool never sees keep their existing widths rather than being guessed at.
  • AC-05: Cell values and formulas are byte-identical to the previous release; only the width declarations change.

Note: The width list had been one entry short since the v2.5 column insertion, so every column from E onward wore its right-hand neighbour's width. Input Source Component carries a deliberate exception to the general width ceiling, because it is the lookup key the Platform A and Platform B formulas read.
